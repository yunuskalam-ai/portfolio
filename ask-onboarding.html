01 / Overview

Answers with receipts.

Ask Onboarding is built for the first weeks at a company, when the handbook is long and the answers are scattered. It ingests PDF, Markdown, and text documents, retrieves the most relevant passages, and asks a local model to answer with citations.

The important product decision is what happens when retrieval is weak. The app does not invent an answer. It refuses, explains that the documents do not cover the question, and drafts a help-desk ticket that a person can review and send.

Design constraint

The whole stack runs locally with no API key: FastAPI, Postgres with pgvector, local embeddings, Ollama, and a React interface.

  • Citation-first answers. Sources are listed under the answer and open beside the chat with the cited passage marked.
  • Honest refusal. Unanswerable questions produce no answer and a drafted ticket instead.
  • Real roles. Employee, manager, and admin permissions are enforced by the server on every request.
  • Operational visibility. Admins get a question log, document gaps, alerts, and an audit trail.

02 / Run instructions

Start it with Docker.

The only setup step is Docker Compose. The first start downloads the Ollama image and the qwen2.5:3b model, so allow a few minutes and about 1.9 GB of disk space. The 18 sample documents load automatically. 

git clone https://github.com/yunuskalam-ai/ask-onboarding.git
cd ask-onboarding
docker compose up

Open http://localhost:8080, choose a demo account, and ask a question on the Chat page. The API docs are available at http://localhost:8000/docs.

Demo accounts and server-enforced roles
Account Role Can
Sam Rivera, Priya Nair Employee Ask questions, open tickets, see their own tickets
Jordan Lee Manager Also see their team’s tickets and browse documents

The demo sign-in has no passwords. Roles, sessions, and permissions are real; a company SSO would replace the sign-in step.

03 / Testing & QA

Quality is part of the product.

CI runs linting, type checks, backend and frontend tests, documentation link checks, and the production build. The test suite has a 95% coverage floor. The repository includes negative and security tests alongside the happy paths. 

# Backend tests
docker compose exec api python -m pytest

# Frontend tests
cd frontend
npm ci
npm test

# Everything CI checks
bash scripts/check.sh

The evaluation uses 20 held-out questions: 16 answerable and 4 deliberately unanswerable. Scoring is strict and repeatable. An answer is correct only when it is not a refusal and contains every key fact. Retrieval is scored separately by checking whether the expected document appears in the top results.

Backend

pytest suite with API, ingestion, retrieval, roles, tickets, and security coverage.

Frontend

Component tests plus a production build check.

Retrieval

Repeatable hit@1, hit@3, and hit@5 checks with no model judge.

Answers

Strict key-fact scoring across answerable and unanswerable questions.

04 / Results

Measured, not assumed.

With the default configuration — 400-character chunks, hybrid search, top 5 sources, and qwen2.5:3b on CPU — the system answered 15 of 16 answerable questions correctly and refused all 4 unanswerable questions.

94% Answer accuracy 15 / 16 answerable
100% Refusal accuracy 4 / 4 unanswerable
100% Retrieval hit@5 Hybrid search
0 False refusals No “I don’t know” on answerable items

Hybrid search combines Postgres full-text search with vector search using Reciprocal Rank Fusion. It moved the right document to rank 1 for questions where vector-only search ranked a related document first. The remaining errors come from the 3B model, not retrieval: it occasionally omits a citation marker or writes a citation where a number belongs.

05 / Limitations

What it does not do yet.

  • CPU latency. The first token can take 8–15 seconds with the local 3B model. A GPU, hosted model, or Claude provider is the fix.
  • Small model mistakes. The 3B model can omit a citation marker or place one where a number should be.
  • Follow-up questions. Earlier turns are sent to the model, but retrieval uses only the current question.
  • Demo sign-in. Accounts are selectable and passwordless; company SSO would replace this step.
  • Uploads only. There is no Google Drive or Confluence sync, and scanned PDFs without a text layer are rejected.
  • English only. The embedding model and full-text search are English.
  • Single-machine scope. Original files live in Postgres, the API runs one process, and ingestion runs inside the API.
  • Small evaluation set. Twenty questions means one question moves accuracy by about six points.
